# Kilo Stable v0.2.0 — Design & Brainstorming Tracker

## Purpose

This document tracks the design work required before implementing **Kilo Stable v0.2.0**.

v0.2.0 is an evolution of the existing Stable v0.1.0 workflow. It is **not intended to become a universal AI development platform**.

The primary objective is:

> Build an opinionated, reliable and cost-conscious Kilo + VS Code workflow that helps me successfully execute my own serious personal software projects from initial idea through implementation and verification.

Expected projects include applications such as:

- MFHistory
- Arthabeacon
- subhbrain
- future personal greenfield projects of similar or greater complexity

The workflow should particularly improve support for **large projects that may run for weeks or months**, where context loss, requirement drift, incomplete decisions and uncontrolled AI behaviour become increasingly problematic.

---

# Scope Rule

Every proposed capability must pass the following test:

> **Does this materially help me design, build, verify or resume my own projects?**

If the answer is unclear, the capability should not be added.

Prefer:

- Kilo-native capabilities
- simple solutions
- explicit workflows
- Markdown/Git where sufficient
- deterministic behaviour where practical
- human-controlled decisions
- measurable improvements

Avoid:

- infrastructure for hypothetical future users
- unnecessary provider abstraction
- generic plugin frameworks
- architecture designed primarily for extensibility
- solving problems we have not encountered or reasonably expect
- building a platform instead of improving the development workflow

---

# Completion Rule

A top-level design item remains unchecked until all important questions underneath it have been answered.

Once there are no material unresolved questions, mark it complete.

The decisions should then be incorporated into the relevant v0.2 specification/documentation.

Completed decisions should not be repeatedly reopened unless later work reveals:

- a contradiction
- an implementation limitation
- new evidence
- or a genuine workflow problem

# Standing Safety Principle

When Kilo cannot confidently classify an authority owner, dependency, impact, reconciliation conflict, lifecycle transition or other workflow-significant ambiguity, it must **not guess**.

It must stop the affected decision path and return:

> **HUMAN_DECISION_REQUIRED**

The response must identify the ambiguity and the concrete choices or missing information needed from the developer. This principle applies across v0.2 and should be reused rather than redefining a different safety rule in each workflow area.

# Recommended Design Order

## [x] 01 — Authority & Reconciliation

### Why this matters

Large projects evolve.

A requirement, architecture decision, external dependency or earlier assumption may change after downstream artifacts have already been created.

Without explicit rules, an AI agent may silently rewrite completed work, ignore the impact of the change, or unnecessarily regenerate large parts of the project.

v0.2 needs a controlled mechanism for handling such changes while keeping the developer in authority.

### Already agreed

- [x] Completed artifacts are immutable during normal downstream work.
- [x] Reconciliation must be explicitly initiated by the human.
- [x] /shouldreconcile evaluates a proposed change before reconciliation occurs.
- [x] /shouldreconcile returns one of:
  - SHOULDRECONCILE
  - NORECONCILENEEDED
- [x] /reconcile executes reconciliation only after the human chooses to proceed.
- [x] Normal implementation changes that can safely be handled by implementation + verification should not automatically trigger reconciliation.
- [x] /reconcile must not reconstruct the project dependency structure from semantic search. Artifact hierarchy and explicit persisted relationships are the source of truth used to calculate reconciliation candidates deterministically.
- [x] Semantic reasoning is used only where semantics are genuinely required: locating the authority root when it is not mechanically obvious, and deciding whether a deterministically discovered candidate is actually affected by the authority delta.
- [x] If the authority root or an impact/conflict classification cannot be made confidently, reconciliation stops that decision path with HUMAN_DECISION_REQUIRED rather than guessing.
- [x] Dependency metadata is maintained by the artifact authoring/grooming workflow; it is not manual bookkeeping left to the developer.
- [x] Readiness gates perform a lightweight local dependency audit using the artifact plus its declared parent, dependencies and immediately relevant authority/context. Broader semantic inspection is used only when the local audit detects uncertainty or possible missing coupling.
- [x] Dependency completeness is best-effort rather than mathematically guaranteed. An undeclared dependency discovered later is recorded as DEPENDENCY_GAP and the metadata is repaired.
- [x] Overlapping reconciliations are allowed. Obligations affecting the same effective work are merged, superseded or escalated; they are not blindly duplicated or used to block the entire project.

### Locked design — exact /reconcile algorithm

Given a human-approved change that has already been classified as SHOULDRECONCILE:

1. **Accept explicit invocation only.** /reconcile never starts automatically.
2. **Locate the authority root(s).** Find the earliest/highest authoritative artifact whose accepted decision must change. Search may identify candidates, but authority ownership is determined from artifact semantics and authority rules. If ownership is ambiguous, return HUMAN_DECISION_REQUIRED and make no speculative authority change.
3. **Create the authority delta.** Record the old accepted decision and the new accepted decision that reconciliation is applying.
4. **Reconcile the root minimally.** Modify only the parts made incorrect by the new decision; unrelated accepted content remains unchanged.
5. **Build the candidate impact graph deterministically.** Read persisted parent/child and explicit dependency metadata and calculate downstream/reverse dependents in memory. Filesystem/directory traversal and repository-wide semantic discovery are not the dependency mechanism.
6. **Classify each candidate semantically.** For every deterministically discovered dependent, ask whether it can remain exactly as written and still be truthful under the authority delta. Unaffected candidates remain unchanged; affected candidates are reconciled; ambiguous cases return HUMAN_DECISION_REQUIRED.
7. **Propagate only through effective change.** Build the complete candidate closure from persisted relationships once, then classify candidates against the effective authority delta. Pass a changed semantic contract along its dependent paths; an unchanged artifact contributes no new delta on that path. Other incoming paths can still affect the same candidate. The detailed propagation and stopping rules appear below.
8. **Record future work changes.** If reconciliation makes planned work obsolete, retain its history and mark it for the appropriate reconciliation retirement state rather than deleting it. If reconciliation requires a new Feature/Spec or other work item, record a required-work obligation; /reconcile does not fully groom or implement that new work.
9. **Assess verification impact.** Reassess prior test and acceptance evidence per claim under the evidence invalidation rules below.
10. **Run a consistency safety scan.** Search for stale authority terms/references and suspicious undeclared coupling after deterministic traversal. This is a backstop, not the primary dependency-discovery mechanism. A newly discovered undeclared dependency is reported as DEPENDENCY_GAP and repaired rather than silently ignored.
11. **Persist a reconciliation work package.** Store a durable reconciliation record containing the authority delta, artifacts checked, artifacts changed, retired work, new required work, invalidated evidence, dependency gaps, unresolved decisions and outstanding delivery obligations.
12. **Return to normal delivery workflow.** Reconciliation restores planning/authority truth and creates mandatory obligations, but it does not force immediate implementation. Unrelated work may continue. Work that depends on an unresolved reconciliation obligation must not be treated as valid/complete until the obligation is resolved through the normal authoring/grooming → /implement → /verify → /review workflow.

The reconciliation work package remains open until its mandatory obligations are resolved. Reconciliation therefore creates **eventual delivery obligations, not mandatory immediate execution**.

### Locked design — RECONCILE_ONLY semantics

**RECONCILE_ONLY is an execution mode for the artifact-owning authoring/grooming agent inside an explicit /reconcile run.** It is not a separate user command, a synonym for /reconcile, or a way for normal downstream work to edit completed authority. /shouldreconcile remains a classifier and does not enter this mode.

- **Entry contract:** /reconcile supplies the accepted authority delta, the reconciliation work-package ID, the specific existing artifact and its role (authority root or dependent), relevant current authority and dependency context, and the reason that artifact was selected. The mode cannot self-start or expand its own scope to another artifact. If the accepted new decision is missing or ambiguous, return HUMAN_DECISION_REQUIRED before changing authority.
- **Permitted change:** Read the artifact as it currently exists, then make the smallest semantic edit needed to bring it into agreement with the accepted delta. Preserve unrelated accepted decisions, stable artifact identity, and a traceable old-to-new delta in Git and the work package. Update relationships and references that become incorrect as part of that edit. A completed artifact can be revised here because the human explicitly initiated reconciliation; normal immutability still applies outside this mode.
- **No effect is a valid result:** If the candidate remains truthful exactly as written, report UNCHANGED with the reason and leave it untouched. A dependency alone does not justify rewriting it. A purely editorial cleanup is outside the reconciliation scope.
- **Unresolved cases:** If an artifact needs a new product/architecture choice, has conflicting authority, or its actual impact is uncertain, return HUMAN_DECISION_REQUIRED with the exact decision and options. Do not invent a decision or mark the artifact reconciled. /reconcile records the blocked branch and can continue independent branches.
- **New or obsolete work:** Report work made obsolete for historical retirement and create only a required-work obligation for genuinely new work. Do not fully author/groom a new Epic, Feature or Spec in this mode; the normal workflow owns that later. Do not implement code, change tests, claim fresh verification, or mark delivery complete.
- **Output contract:** Return the artifact ID; CHANGED, UNCHANGED, or HUMAN_DECISION_REQUIRED; the reason; exact semantic delta or unchanged rationale; relationship/reference corrections; potential downstream contracts affected; newly discovered dependency gaps; and any retirement, new-work, or verification-review obligations. /reconcile owns graph traversal, propagation, work-package persistence, and handoff to normal delivery.
- **Resume and overlap:** On resumption, re-read current artifacts and the open work package before editing. If another reconciliation already made the same effective change, merge/supersede the obligation and report UNCHANGED. If accepted deltas conflict or the current artifact no longer matches the assumed baseline, return HUMAN_DECISION_REQUIRED for that path. Never replay a stale patch blindly.

This mode restores the truth of existing planning artifacts and records obligations. It does not certify that code or prior evidence still satisfies the revised authority; the dispositions, propagation boundaries and evidence rules below govern that assessment.

### Locked design — impacted-artifact disposition

Track the result for each existing candidate **in the reconciliation work package**, separately from its normal artifact lifecycle state. This is a per-reconciliation assessment, not a second global lifecycle state machine.

| Disposition | Meaning |
| --- | --- |
| `UNCHANGED` | Checked against the accepted authority delta and remains truthful as written; no artifact edit. |
| `REVISED` | Existing artifact was minimally updated under RECONCILE_ONLY; record the effective semantic delta. This does not mean code or verification obligations are complete. |
| `DECISION_REQUIRED` | Impact, authority, or the required revision cannot be settled confidently; preserve the artifact and record the exact human decision needed. The affected path remains blocked while independent work may continue. |
| `RETIRE_REQUIRED` | Existing planned work has become obsolete; retain its history and record the obligation to move it to the eventual retirement lifecycle state. Do not delete it. |

`NEW_WORK_REQUIRED` is a work-package obligation, not the disposition of a nonexistent artifact. Normal artifact lifecycle and retirement transitions will be specified under Point 05.

The RECONCILE_ONLY agent's `CHANGED` result is recorded as `REVISED` in the work package; its `HUMAN_DECISION_REQUIRED` result is recorded as `DECISION_REQUIRED`. A disposition describes the current result of this reconciliation assessment, not whether delivery has been implemented or freshly verified.

### Locked design — previous verification evidence after reconciliation

A passing test run or human acceptance remains a historical observation. Its **applicability to a current claim** is what reconciliation reassesses. Evidence becomes inapplicable the moment the accepted claim it was used to prove changes, even if implementation and tests have not yet changed. /reconcile does not execute tests or claim new verification.

- Assess applicability per **claim-to-evidence association**, not per whole test run. One integration or E2E run may support several Spec or Feature claims. If only SPEC-A's claim changes, its association becomes invalid for the revised claim; the same run may still support SPEC-B's unchanged claim, provided the test behavior, relevant implementation, environment and assumptions still support B. Preserve the run and its history. A shared changed premise or changed assertion may affect both associations; assess them rather than assuming B is safe.
- A revised requirement, contract, architecture assumption, acceptance criterion or governing authority invalidates previous evidence for the affected claim. A new expected behavior requires the appropriate tests/acceptance checks to be updated and run through normal delivery. A purely editorial revision that leaves the claim and its premises unchanged does not invalidate evidence.
- For changed shared behavior, evaluate the evidence associations of actual dependents. Require targeted Spec checks and relevant Feature integration/E2E or human acceptance where the affected claims need them; do not automatically discard an entire suite's results or demand a full project rerun. Ordinary implementation changes classified NORECONCILENEEDED still use the normal verification process.
- If a candidate artifact is UNCHANGED and its claim, tested behavior and relevant premises remain valid, retain its evidence association as applicable. If applicability cannot be established confidently, record the precise uncertainty and return HUMAN_DECISION_REQUIRED for the affected path; do not silently count that evidence as current.
- In the reconciliation work package record affected claim(s), prior evidence reference(s), applicability decision and reason, and the required reverification scope. Treat reverification as a mandatory delivery obligation, not as an impacted-artifact disposition or a second artifact lifecycle state. Do not mark affected acceptance as currently verified/complete while its required evidence is outstanding; the exact lifecycle representation belongs to Point 05.
- Reverification obligations follow the existing reconciliation overlap rule. Match obligations for the same effective claim and verification target; merge compatible outstanding work with links to every originating REC record. If a later accepted delta changes that target, supersede the obsolete target/obligation with the latest one while retaining its history. If accepted deltas conflict or the required target is uncertain, escalate under HUMAN_DECISION_REQUIRED rather than opening competing obligations. Close the effective obligation only when fresh applicable evidence is produced through the normal /implement → /verify → /review path.

The exact evidence metadata and Feature verification criteria are deferred to Points 05 and 09; they must preserve these claim-level applicability and overlap semantics.

### Locked design — propagation through dependents and stopping

- From the approved authority root(s), /reconcile computes the bounded downstream candidate closure **once** using the persisted hierarchy and explicit reverse dependencies. Candidate discovery is deterministic; semantic search does not construct or recursively expand the graph. Classify the candidates for effective impact, preserving unchanged artifacts and independent paths.
- The accepted authority delta is the input to root assessment. A `REVISED` artifact passes only its effective semantic/contract delta to dependent candidates. `UNCHANGED` passes no new delta along that path; a candidate reached independently by another changed path is still assessed. Combine compatible incoming effects on one candidate and record one disposition/obligation for the effective work; conflicting effects require HUMAN_DECISION_REQUIRED.
- `RETIRE_REQUIRED` preserves the obsolete work's history and records its retirement obligation; evaluate existing dependents whose premise changes. `DECISION_REQUIRED` suspends the affected path and records the precise human decision as an open obligation. Continue independent paths. Do not guess past a blocked decision or count it as resolved.
- `NEW_WORK_REQUIRED` is a delivery obligation handed to normal authoring/grooming. It is not a newly authored graph node for this /reconcile run and does not recursively expand reconciliation. Reverification obligations likewise pass to normal delivery.
- Once candidate assessment reaches `UNCHANGED`, `REVISED` with all relevant existing dependent paths assessed, `RETIRE_REQUIRED` with its dependent impact assessed, or a recorded blocked `DECISION_REQUIRED` path, perform **one bounded consistency safety scan** for stale references or undeclared coupling. A discovered `DEPENDENCY_GAP` is recorded and its persisted metadata repaired; assess any newly identified impact before declaring the work package assessment complete. This is a bounded correction, not a repeated repository-wide discovery loop. If its impact or repair cannot be settled, record HUMAN_DECISION_REQUIRED for that path.
- /reconcile may finish when the accepted authority updates and all known candidate/effective-change paths have been assessed or explicitly blocked, the bounded safety scan and any discovered gap assessment have been handled, and the reconciliation work package durably records every remaining human decision and delivery obligation. It does **not** wait for implementation, new-work grooming, retirement execution, or reverification. The work package stays open until mandatory obligations are resolved; affected work cannot be claimed complete while its obligations remain.

## [x] 02 — Dependency & Impact Model

### Why this matters

Reconciliation and context selection cannot work reliably unless Kilo understands how project artifacts depend on one another.

The normal hierarchy is:

Epic → Feature → Spec → Implementation → Tests

But dependencies may also exist sideways, for example:

- SPEC-A depends on SPEC-B.
- FEATURE-A depends on a Platform Feature.
- SPEC-C is governed by an Architecture Decision.

### Established constraints from Point 01

- Dependency relationships required for reconciliation must be available deterministically from persisted artifact relationships/metadata; /reconcile must not reconstruct the graph from semantic search.
- The dependency graph may be calculated in memory from authoritative artifact metadata; a separately maintained duplicate graph is not required by Point 01.
- Semantic inspection remains a bounded safety/impact mechanism, not the primary dependency-discovery mechanism.
- Dependency metadata must be maintained during authoring/grooming and receive a lightweight local audit at readiness gates.
- Silent dependency gaps remain an accepted residual risk; when discovered they must be surfaced as DEPENDENCY_GAP and repaired.

### Locked design — dependency relationships (Point 02.1)

- **Contains:** The structural parent/child relationship (for example, Epic → Feature → Spec). Derive it deterministically from the artifact's persisted ID/location convention; authors do not maintain a separate `contains` field. Point 05 defines the exact identity/location format. This relationship is available to reconciliation as a persisted structural fact, not guessed from semantic search.
- **Governed by:** An artifact is constrained by an accepted authority decision, whether an ADR, a PRD clause, an Epic policy or another authoritative decision. This is not ADR-specific. The governing decision must be identifiable from authoritative metadata; Point 05 defines its exact reference shape.
- **Depends on:** An artifact relies on another artifact's decision, behavior or contract remaining true. This can cross parent/Feature boundaries; the precise cross-Feature audit rule remains open below.

These are the only relationship meanings required at this level. A link makes an artifact a **candidate** for impact assessment, not automatically an impacted artifact. Point 01's effective-delta and semantic classification rules still apply. Test/evidence associations are assessed per claim under Point 01's evidence rules; they are not an additional dependency type here.

### Locked design — cross-cutting concern coverage (Point 02.6)

- A cross-cutting concern is represented by an accepted authority decision (for example an ADR, PRD clause or Epic policy). It does not create a new dependency type.
- Use the existing **Governed by** relationship to declare applicability. Persist it at the highest artifact scope where the policy applies uniformly. Descendants inherit that governing context through the derived Contains hierarchy.
- If applicability begins only at a narrower scope, declare Governed by at that narrower Feature or Spec rather than widening scope merely to reduce metadata.
- Inherited governance is derived coverage, not another persisted edge. Kilo may report that a descendant is governed through an ancestor while preserving the ancestor's Governed by edge as the authoritative fact.
- Do not maintain a mirrored authority-side `governs` list. Reverse lookup derives affected scopes from authoritative Governed by references and structural containment.
- **Explicit exemption is supported as a governance-coverage override, not a fourth dependency relationship.** An artifact may declare `Exempted from <authority-ref>` when an inherited authority deliberately does not apply at that scope. The exemption suppresses inheritance for that authority only; all other inherited authorities remain in force.
- Exemption is explicit and positive metadata. Absence of Governed by or absence of enforcement must never be interpreted as an exemption.
- **An exemption cannot self-authorize.** Every `Exempted from <authority-ref>` declaration must carry an `Authorized by <decision-ref>` reference to an accepted decision with sufficient authority to permit that override. `Authorized by` is authorization metadata for the exemption, not a new dependency type.
- **Authorization must explicitly address the override.** The authorizing decision must explicitly reference either the governing authority being overridden or the specific scope/artifact receiving the exemption. Merely pointing to an unrelated accepted decision at a qualifying authority tier is invalid.
- If no accepted decision explicitly authorizes the exemption, or the authorization's applicability is ambiguous, the artifact cannot treat the exemption as effective and readiness must raise HUMAN_DECISION_REQUIRED rather than silently accepting it.
- Changes to either the governing authority or the authorizing decision make the exemption's effective coverage subject to reconciliation through the normal authority/dependency rules.
- A narrower descendant may re-enter the authority's coverage only through an explicit direct Governed by declaration for that authority; do not infer re-entry automatically below an exemption.
- Readiness grooming resolves effective governing context from direct Governed by references, inherited governing context, and explicit exemptions. Missing or contradictory coverage is surfaced as DEPENDENCY_GAP; unresolved ambiguity follows HUMAN_DECISION_REQUIRED.
- Authority changes enter reconciliation through authoritative Governed by edges. Structural descendants in effective coverage become candidates through Contains; exempted subtrees are excluded for that authority unless a descendant explicitly re-enters coverage. Candidate status still does not imply effective impact; Point 01 semantic classification applies.
- Point 02.6 owns only deterministic policy applicability/coverage. Point 10 owns how any resulting Platform, Enabler, shared-infrastructure or ordinary Feature work is packaged and scheduled.

This preserves the Point 02.1 relationship model while making cross-cutting exceptions first-class and deterministic.

### Locked design — upstream dependency discovery (Point 02.3)

- **At authoring/grooming:** Starting from the artifact's derived parent and accepted authority, identify decisions, behavior and contracts that the artifact actually relies on. The authoring workflow records the relevant Governed by and Depends on references on the dependent artifact. This is the bounded semantic identification pass; it does not maintain a mirrored reverse list.
- **At readiness:** Audit the artifact locally against its parent, declared dependencies and immediately relevant authority/context. Inspect more broadly only when that audit reveals uncertainty or possible missing coupling. Do not repeatedly run repository-wide semantic discovery at every lookup.
- **At lookup:** Derive the structural parent from persisted ID/location and follow declared Governed by/Depends on references upstream as needed. A missing relationship is not inferred from code, prose search or file proximity to manufacture a resolved graph edge. Point 01's bounded safety scan can discover a DEPENDENCY_GAP; repair its authoritative metadata and reassess affected work.
- **Target not yet authored:** Record a pending dependency describing the required contract, expected owner if known, and work needed to establish it. Do not put a nonexistent target ID in a resolved-looking Depends on reference. If an existing accepted authority already settles the contract, reference that authority; link the eventual target when it exists. If the necessary contract remains undecided, the dependent artifact cannot pass readiness.
- **Make the blocker actionable:** An undecided contract in a pending dependency creates or links to a tracked grooming obligation in the expected owner's scope, using the existing required-work handoff pattern. Avoid duplicate obligations for the same effective work. If the owner or decision cannot be identified confidently, use the standing HUMAN_DECISION_REQUIRED rule and keep that path blocked. When the target and contract exist, replace the pending entry with the real reference and repeat the local readiness audit.

Point 05 defines the exact pending-reference, obligation and lifecycle representation. The cross-Feature audit boundary and cross-cutting policy coverage remain open under their own Point 02 items.

### Locked design — cross-Feature dependencies (Point 02.5)

- A cross-Feature dependency is **not a separate dependency type**. It is an ordinary `Depends on` relationship whose target happens to belong to another Feature or Epic. The same dependency semantics, readiness audit, reverse lookup and reconciliation rules apply across boundaries.
- **Declare the dependency at the lowest artifact that genuinely owns the reliance.** If one Spec relies on another Feature's Spec-level contract, persist Spec → Spec. Persist Feature → Feature only when the consumer Feature as a whole genuinely relies on the provider Feature's capability or contract.
- **Do not auto-promote or duplicate derived relationships.** Repeated Spec-level dependencies do not create a separately persisted Feature-level dependency, and transitive closure is not persisted merely for convenience. Higher-level Feature/Epic dependency views are derived from authoritative edges when needed.
- **Multiplicity does not change ownership level.** Ten independent Spec-level dependencies on another Feature remain ten authoritative Spec-level dependencies if each reliance genuinely belongs to those Specs. A Feature-level dependency exists only when there is a real Feature-level invariant or contract owned at that level.
- **Derived roll-up is informational, not authoritative.** Kilo may report that Feature A depends on Feature B through multiple lower-level edges for grooming, context or impact summaries, but reconciliation traverses the underlying authoritative edges rather than treating the roll-up as another dependency.
- **A later-discovered Feature-level invariant does not collapse existing lower-level edges.** Add the genuine Feature-level dependency alongside the existing Spec-level edges as its own authoritative fact. Existing Spec-level edges remain unchanged unless someone deliberately re-scopes their ownership; never merge or delete them merely because a higher-level contract was discovered.
- **Provider implementation is not automatically a grooming prerequisite.** A consumer may proceed once the contract it relies on satisfies the lifecycle/readiness condition required for safe consumption; **Point 05 must define the exact state vocabulary and lifecycle condition for that contract.** Point 02 establishes only the dependency semantics and must not invent an independent “accepted/stable” state.
- If the required target or contract does not yet satisfy that Point-05-defined condition, use Point 02.3's pending-dependency and tracked grooming-obligation rules. The consumer cannot pass its relevant readiness gate while the required contract remains undecided.
- Dependency ordering does not automatically equal implementation ordering. A consumer may be implemented against a sufficiently established contract before the provider is complete, but it cannot be claimed fully integrated/verified/complete while required provider capability or integration evidence remains outstanding. Points 05 and 09 define the exact lifecycle/completion representation.
- Provider changes propagate through the actual declared cross-Feature edge using Point 01's deterministic reverse lookup and semantic impact classification. Crossing a Feature or Epic boundary does not itself make a candidate impacted.
- **Dependency cycles are readiness blockers when they prevent either side from establishing a usable contract independently.** Kilo must not invent execution ordering to hide the cycle. First check whether the contract belongs under an existing shared/higher authority or whether decomposition/ownership is wrong; if the correct resolution cannot be determined confidently, return HUMAN_DECISION_REQUIRED.
- **Cycle detection is an ongoing invariant, not a one-time grooming check.** Re-run the relevant cycle check whenever a new or changed dependency edge is persisted, including during later grooming, reconciliation metadata repair, or dependency-gap repair. A previously READY artifact may therefore require readiness re-evaluation if a later edge introduces a blocking cycle; Point 05 defines the exact lifecycle transition/state effect.

This keeps cross-Feature coupling explicit without creating a second dependency model or a duplicated Feature-level graph.

### Locked design — meaningful impact for dependency traversal (Point 02.7)

- **Point 02.7 owns propagation candidacy, not the reconciliation decision.** It answers whether an effective semantic delta on the source side of a relationship touches the premise represented by that relationship strongly enough that the dependent/covered artifact must be reconsidered as a candidate. Point 01's `/shouldreconcile` remains solely responsible for deciding whether the requested change warrants reconciliation.
- **Universal premise test:** a change propagates across a relationship only when the effective semantic delta changes a premise represented by that relationship. "Artifact changed" is not equivalent to "dependency premise changed."
- **Depends on:** propagate when the provider's behavior, contract, invariant or decision actually relied upon by the consumer changes. Internal refactoring, logging, formatting, implementation-detail changes or other non-observable changes do not propagate when the relied-upon premise remains unchanged.
- **Governed by:** apply the same semantic-delta rule to authority documents. Propagate only when the enforceable constraint changes — what the governed scope is required, permitted or forbidden to do, or the applicability of that constraint. Typographical fixes, rationale clarification, examples, section reordering or wording cleanup that do not change the effective rule do not propagate.
- **Contains:** containment alone does not mean every descendant is impacted whenever an ancestor changes. Contains provides the structural path for effects such as inherited governance, decomposition/retirement or other structural deltas; propagation still requires that the effective delta changes a premise relevant to that descendant.
- **Governance overrides:** `Exempted from` / `Authorized by` remain governance-coverage metadata rather than dependency types. Reconsider coverage when the governing rule, exemption, authorizing decision or their applicability changes in a way that may alter the effective governing context.
- **Safe ambiguity default:** when Kilo cannot determine confidently whether the semantic delta touches the represented premise, propagate the artifact as a candidate rather than silently suppressing it. This conservative step does not itself mean the artifact is impacted or that reconciliation is required; subsequent semantic classification and `/shouldreconcile` retain those decisions. If the ambiguity itself requires an authority decision to resolve, use the standing HUMAN_DECISION_REQUIRED rule.
- A propagated candidate may still classify as unchanged after inspection. Candidate propagation is therefore intentionally broader than effective impact.
- Point 05 owns the exact lifecycle/state consequences of material versus non-semantic artifact changes. Point 02.7 defines only the dependency-traversal meaning of "meaningful impact."

**Concrete anchor:** if Spec B depends on Spec A's `CreateOrder(request) -> OrderId` contract, renaming a private class, adding tracing or optimizing persistence does not propagate when observable behavior is unchanged. Changing the request schema, response semantics, accepted-input invariant or removing behavior B relies on does propagate B as a candidate. The same distinction applies to authority artifacts: "must support OAuth2" → "must support OAuth2 with PKCE" propagates; reorganizing the ADR or clarifying its rationale without changing the enforceable rule does not.

- [x] How upstream dependencies are discovered — authoring/grooming identification, local readiness audit and persisted-reference lookup, with pending targets linked to tracked grooming obligations as defined above.
- [x] How downstream impact is discovered — one-time deterministic reverse lookup and candidate closure over persisted relationships; semantic classification follows candidate discovery.
- [x] How cross-feature dependencies work.
- [x] How cross-cutting concerns are represented.
- [x] What constitutes a meaningful impact.
- [x] Which dependencies must be persisted — the structural ID/location must make hierarchy derivable, and explicit Governed by/Depends on relationships needed for candidate discovery must be persisted in authoritative artifact metadata. No separate authored Contains field or duplicate graph is required. Other safe-inference boundaries remain open below.
- [x] Which dependencies can simply be inferred when needed — safe inference is limited to deterministic, lossless derivation from authoritative persisted facts. Kilo may derive structural ancestry/descendants from artifact identity/location; inherited and effective governance from direct Governed by, containment, exemptions and explicit re-entry; reverse dependents from declared Depends on/Governed by references; transitive closures for reconciliation/context assembly; and informational higher-level roll-ups from underlying authoritative edges. Derived relationships are computed when needed and are not persisted as duplicate authoritative edges.
- [x] Kilo must not infer semantic Depends on or Governed by relationships from code, prose similarity, naming, file proximity, call patterns or architectural intuition; must not infer exemptions or authorization; must not promote lower-level dependencies into authoritative higher-level dependencies; and must not turn pending dependencies into resolved references without an accepted target/contract. If semantic inspection reveals a missing relationship, record DEPENDENCY_GAP, repair authoritative metadata and recompute derived views. If the correct relationship cannot be established confidently, use HUMAN_DECISION_REQUIRED.
- [x] Structural changes are deltas, not harmless inference updates. If an artifact's persisted identity/location changes in a way that changes its derived Contains relationship (for example, reparenting a Spec to another Feature or a Feature to another Epic), treat that structural change as an effective dependency-context delta. Recompute inherited/effective governance, ancestry-dependent context and derived roll-ups, then propagate candidates wherever those effective premises change. The move does not require a persisted Contains edge, but it must not be treated as a purely mechanical rename/move with no impact assessment.
- [x] Persistence rule: **Persist meaning; derive mechanics — but when the authoritative facts from which mechanics are derived change, reassess the semantic consequences of the derived relationships.**
- [x] How dependency information participates in reconciliation — Point 01's deterministic candidate traversal, effective-delta propagation, bounded safety scan and DEPENDENCY_GAP repair.

### Expected outcome validation

Point 02 was acceptance-checked end-to-end against three representative change paths:

1. **Ordinary contract dependency:** `SPEC-CHECKOUT` explicitly Depends on `SPEC-ORDER-CREATE`'s `CreateOrder(request) -> OrderId` contract. A material request/response/invariant change makes Checkout a deterministic downstream candidate; internal refactoring, tracing or persistence changes that preserve the relied-upon premise do not. Cross-Feature roll-ups may be derived for reporting but do not create duplicate authoritative Feature-level edges. Candidate status still does not mean rewrite or reconciliation disposition; Point 01 performs semantic classification.

2. **Structural/derived relationship change:** reparenting an artifact changes its derived Contains relationship even if artifact content does not change. Kilo recomputes ancestry, effective governance and derived roll-ups and propagates candidates only where those effective premises change. This validates that deterministic structural edits cannot silently alter semantic context without impact assessment.

3. **Governance/exemption/authorization chain:** `FEATURE-A` is Governed by `ADR-007`; `SPEC-CHECKOUT` inherits that governance but declares `Exempted from: ADR-007` with `Authorized by: ADR-009`, where ADR-009 explicitly permits the override. Effective coverage therefore excludes SPEC-CHECKOUT. If ADR-009 later revokes that authorization, the authorization premise changes, the exemption becomes ineffective, ADR-007 coverage is recomputed as active, and affected artifacts become candidates under the normal premise test. An exemption without valid explicit authorization does not suppress inherited governance; unrelated authority wording changes do not alter coverage; ambiguity uses HUMAN_DECISION_REQUIRED. A change to ADR-007 itself correctly does not propagate into a subtree that remains validly exempt from ADR-007, because that subtree is not effectively governed by it.

Together these checks exercise ordinary dependency traversal, structural derived-context change, and the full Governed by → Exempted from → Authorized by chain while preserving the core distinction:

> **candidate ≠ effective impact ≠ required rewrite/reconciliation disposition**

Enough dependency information now exists for Kilo to answer:

> **If this changes, what actually needs reconsideration?**

without attempting to construct a universal software dependency graph.

## [x] 03 — Context Freshness & Context Management

### Why this matters

Large-project AI workflows eventually fail if every agent receives either too little context, causing incorrect decisions, or too much context, increasing token consumption and distracting the model with irrelevant information.

v0.2 needs deliberate context management.

### Locked design — stage context requirements (Point 03.1)

Each workflow stage starts from a **minimum-sufficient context contract**: its direct authority chain, its immediate working artifact(s), and only the dependency/governing context materially relevant to the task. Broader project context is discovered on demand rather than preloaded.

| Workflow stage | Mandatory starting context | Loaded only when relevant |
| --- | --- | --- |
| **Ideation** | Project identity, existing/resumed Ideation artifact, previously answered and unresolved questions | Prior research, existing-product/code context when evolving an existing system rather than starting greenfield |
| **PRD authoring** | Completed Ideation artifact in full | Relevant research/evidence referenced by Ideation; existing PRD only during reconciliation |
| **Architecture** | **PRD in full**, existing accepted ADR index/summary | Full specific ADRs, technical research, existing code/repository facts needed for an architectural decision |
| **Epic grooming** | Relevant PRD sections, applicable architecture/ADRs, Epic artifact | Cross-cutting authorities and dependencies affecting that Epic |
| **Feature grooming** | Parent Epic, relevant PRD requirements, applicable architecture/governance, Feature artifact | Other Features/contracts on which the Feature depends |
| **Spec grooming** | Parent Feature, directly relevant Epic/PRD requirements, applicable ADR/governance, Spec artifact, declared dependencies/pending dependencies | Full dependency artifacts when their contracts cannot be understood from bounded references/contract summaries |
| **Implementation** | Current Spec in full, directly applicable authority/contracts, implementation workspace/code relevant to the Spec | Related source files, dependency Specs/contracts, ADR details, tests and prior implementation notes discovered as needed |
| **Verification** | Current Spec/Feature acceptance claims, implementation under test, relevant test/evidence context | Dependency/provider evidence, affected ADR/PRD clauses and broader regression context when required |
| **Review** | Artifact/work being reviewed, governing requirements, relevant verification evidence | Parent/adjacent artifacts where consistency must be checked |
| **/shouldreconcile** | Proposed change, artifact/decision it appears to affect, enough authority context to classify whether accepted truth changes | Dependency information only where needed to determine whether this is an authority-level change rather than ordinary implementation work |
| **/reconcile** | Accepted change, authority root, current reconciliation work package, authoritative artifact/dependency metadata required for deterministic candidate discovery | Full candidate artifacts as each candidate is semantically assessed; bounded consistency-scan context |
| **Resume / CONTINUE** | Current authoritative artifact, durable workflow checkpoint/state, unresolved decisions/obligations | Prior conversation only when it contains information not yet persisted; that condition is a workflow defect rather than normal context |

The following rules are locked for stage-level context assembly:

1. **Stage-scoped contracts.** Each workflow stage has a defined mandatory starting set and an on-demand expansion set.
2. **Working artifact in full.** The artifact currently being authored, reconciled or verified is not reduced to a summary.
3. **Authority/dependency context is relevance-scoped.** Load the governing decision or relied-upon contract rather than automatically loading the complete source artifact.
4. **PRD → Architecture asymmetry.** Architecture always receives the full PRD because system-wide requirement interactions can be hidden by aggressive slicing. Downstream Epic, Feature, Spec and implementation stages remain bounded.
5. **Broader context is pull-based.** Additional context is discovered only when the starting context exposes a genuine need; unrelated project knowledge is not preloaded.
6. **Persisted project truth beats conversational memory.** A stage must be reconstructable from repository/workflow state alone after a fresh session, including weeks or months later. Chat history may assist conversational continuity but is not authoritative project context.

Structural ancestry does not by itself justify loading every ancestor artifact. Point 02's Contains, Governed by and Depends on relationships identify where relevant context may come from, but context assembly still selects only the authority decisions, contracts and artifact content necessary for the current stage.

This point deliberately does **not** yet define snippet/reference representation, freshness markers, stale-context detection, context ceilings, retrieval mechanics or token-budget rules; those remain under the later Point 03 questions.

### Locked design — agent context requirements (Point 03.2)

An agent's context is the context contract of the workflow stage it is executing (per Point 03.1), plus the minimum role-specific context required to exercise that agent's authority.

The following rules are locked:

1. **Stage context + role overlay.** The workflow stage defines the base context contract; the agent receives only the additional role-specific context required to exercise its authority. Point 03.2 does not duplicate complete stage-context contracts per agent.
2. **Delegation is bounded, not inherited.** Agents do not inherit the caller's full context. Delegation assembles a deliberate, bounded context packet rather than copying the parent's conversational or working context.
3. **Fresh-review agents deliberately receive less.** Adversarial/fresh-review agents receive the reviewable artifact plus its governing contract, with factual evidence retrieved on demand. They do not receive the author's reasoning trail or preferred conclusion.
4. **Context follows authority, not model identity.** Model variants performing the same logical role use the same context contract. Switching model/provider does not change what project truth the role is entitled or required to receive.
5. **Durable reconstruction is mandatory.** All mandatory agent context must be reconstructable from durable project/repository state. Prior chat history may assist conversational continuity but must never be the only source of required project truth.

#### Illustrative current-agent mapping — non-normative

The current working agents can be understood under these rules as follows: Planner and Planning Worker consume the applicable planning-stage context plus their delegated workflow/mode state; Builder consumes implementation-stage context plus relevant workspace state; Debugger consumes the exact failure/reproduction evidence plus affected contracts and implicated code/tests/configuration; adversarial agents consume the smallest artifact + governing contract; reviewers consume the current change, governing requirements and verification evidence; smoke orchestration/execution agents consume only the smoke state and delegated workflow context required for their responsibilities.

This mapping is **illustrative only** and does not establish the final v0.2 agent roster, names or ownership boundaries. Those are reserved for **Point 07 — Commands & Agents**. Any final agent defined there must conform to the context rules above.

The existing `planning-worker.md` RECONCILE_ONLY wording discrepancy is noted for Point 07 and is deliberately not resolved under Context Management.

### Locked design — mandatory versus optional context (Point 03.3)

Context classifications are **conceptual reasoning labels only**, not persisted artifact metadata or schema fields. No classification machinery is added unless later design work under Points 05 or 07 demonstrates a concrete need for it.

Use these context classes when assembling or reasoning about a stage/agent request:

- **MANDATORY_START** — required before the stage or agent can begin meaningful work.
- **MANDATORY_ON_DEMAND** — not required initially, but becomes mandatory once work in progress establishes its relevance; retrieve it before the affected decision and never guess around it.
- **OPTIONAL** — safely omittable without changing correctness, authority or valid completion; omission may reduce speed, convenience or explanatory richness only.
- **EXCLUDED** — deliberately withheld by the role contract because receiving it would compromise the role's purpose. Exclusion is a deliberate design choice, not another form of optional context.

The following rules are locked:

1. **Correctness test.** If omitting context could cause violation of accepted requirements, authority, dependency contracts, current workflow state or acceptance criteria, that context is mandatory.
2. **Mandatory does not mean preload.** MANDATORY_ON_DEMAND exists specifically so correctness does not require preloading every potentially relevant artifact or dependency.
3. **Relevance promotes context.** When the current work exposes a material dependency, governing decision, unresolved obligation, external contract or factual prerequisite, the necessary source becomes mandatory for that decision path.
4. **No guessing past missing mandatory context.** If mandatory context cannot be retrieved, stop the affected decision path. If the issue is genuinely ambiguous rather than merely unavailable, use the standing HUMAN_DECISION_REQUIRED principle.
5. **Optional context cannot secretly carry authority.** If material initially treated as optional reveals an authoritative fact, retrieve the relevant authoritative source and treat it as mandatory before relying on that fact.
6. **Optional means safely omittable.** Removing optional context must not change what the agent is authorized to decide, whether its result is valid, or whether completion can legitimately be claimed.
7. **Chat history remains non-mandatory.** Required project truth must be reconstructable from durable repository/workflow state. Prior conversation may help continuity but must never be the only source of mandatory context.

Core rule:

> **Context is mandatory when correctness, authority, or valid completion depends on it. Mandatory context may be required at stage entry (MANDATORY_START) or become mandatory once the work in progress establishes its relevance (MANDATORY_ON_DEMAND). Context is OPTIONAL only when it can be safely omitted without changing the validity or authority of the result. Role contracts may additionally EXCLUDE context that would compromise the role's purpose.**

### Locked design — context freshness establishment (Point 03.4)

Context freshness is established by resolving every mandatory context item from its current authoritative source when the task context is assembled — not by how recently that text happened to be generated. Freshness is tied to current source content, including uncommitted working-tree state, rather than conversation age, cached summaries, or Git commit time alone. Each agent invocation works from a bounded fresh snapshot assembled at start; mandatory context discovered later (`MANDATORY_ON_DEMAND`) is freshly resolved at the moment it becomes relevant, never pulled from an earlier cached copy. Delegation always re-establishes freshness independently — a caller passes task intent, identifiers, scope and workflow mode, never its own already-expanded context as if it were authoritative.

The following rules are locked:

1. **Assembled, not inherited.** Every invocation reconstructs mandatory context from current repository/workflow state according to Points 03.1–03.3. It never assumes that prior conversation context, an earlier agent invocation, a cached summary or a previous execution still represents current project truth.
2. **Resolve at assembly time.** For each `MANDATORY_START` item, determine its authoritative source, resolve its current location/reference, read its current content or required portion, and record which source revision supplied it. Apply the same rule to `MANDATORY_ON_DEMAND` context when relevance is established.
3. **Working tree, not just commits.** Freshness identity is conceptually the artifact/reference plus a fingerprint of its current content, including uncommitted working-tree changes, rather than merely a Git commit SHA. Exact hash/fingerprint mechanics are deferred to implementation design and are not decided here.
4. **Bounded snapshot per invocation.** Once assembled, the initial packet is the current-project-truth snapshot for that invocation. Kilo does not continuously re-read every source while the agent is reasoning. Newly required `MANDATORY_ON_DEMAND` context joins the snapshot when retrieved. Changes that occur after assembly and how they are detected belong to Point 03.5.
5. **Summaries/references do not self-certify freshness.** A summary, compact contract or stored reference may be used as context representation where later rules allow it, but when it is mandatory its freshness must be established against the current authoritative source rather than trusted because the representation was generated previously.
6. **Delegation re-resolves independently.** A delegated agent receives task intent, identifiers, scope and workflow mode, then assembles its own stage + role context from current authoritative state. The caller's already-expanded context is not inherited as authoritative truth. This prevents stale context from cascading through agent chains, including future cross-model handoffs.

Core rule:

> **Freshness means current authoritative source truth was resolved for this invocation, not that the text happens to be recent.**

### Locked design — stale information detection (Point 03.5)

Context becomes stale when an authoritative source the current reasoning depends on no longer matches the source revision resolved into the invocation — not by elapsed time. Detect this through targeted source-fingerprint revalidation at meaningful workflow boundaries; refresh only the affected context; reassess only the reasoning that depended on the changed source.

The following rules are locked:

1. **No continuous polling.** Checks happen at workflow boundaries, not continuously while an agent is reasoning.
2. **Mandatory context carries resolved-source identity.** Conceptually record artifact/reference + source location + content fingerprint for mandatory context. Exact hashing/fingerprint mechanics remain deferred to implementation, per Point 03.4.
3. **Revalidate at meaningful boundaries.** Re-check relevant mandatory-source fingerprints before finalizing a stage result; when `MANDATORY_ON_DEMAND` context is pulled into an active invocation; when resuming after interruption/checkpoint; and when the workflow observes out-of-band repository/worktree changes.
4. **Changed fingerprint requires re-read.** Once the authoritative source no longer matches the resolved source identity, do not continue relying on the old copy, summary, contract extract or cached representation. Re-read the authoritative source.
5. **Use targeted invalidation.** A stale source does not invalidate the entire context packet automatically. Refresh that source and revisit only reasoning or outputs that actually depended on it.
6. **Semantic change, not byte change, determines impact.** A content fingerprint change triggers refresh, but the refreshed source may prove semantically unchanged for the current task (for example spelling or formatting cleanup). In that case existing reasoning may remain valid. A changed governing decision or contract requires the affected reasoning to be reassessed.
7. **An agent's own expected edits are not external staleness.** Deliberate writes to the invocation's active output/implementation targets are tracked as part of that work, not treated as an authority/source changing underneath it.
8. **Derived representations inherit source freshness.** A summary, compact contract or extract derived from source fingerprint A becomes stale when the authoritative source becomes fingerprint B until it is validated or regenerated against the current source. Points 03.6/03.7 decide when such representations are allowed.
9. **Do not guess through genuine conflict.** After refresh: if the work remains valid, continue; if affected reasoning can be deterministically recomputed, redo that path; if the changed authority creates genuine ambiguity or conflicting accepted truth, use the standing `HUMAN_DECISION_REQUIRED` principle.

Explicitly excluded from v0.2 stale detection: filesystem watchers, background refresh, TTLs, context-age rules, periodic rescanning and a separate stale-context database.

Core rule:

> **Context becomes stale when an authoritative source on which the current reasoning depends no longer matches the source revision resolved into the invocation. Detect this through targeted source-fingerprint revalidation at meaningful workflow boundaries, refresh only affected context, and reassess only reasoning dependent on the changed source.**

### Locked design — when full artifacts are needed (Point 03.6)

Load an artifact in full only when the task requires understanding, modifying, validating, or judging the artifact as a whole, or when its relevant semantics cannot be safely isolated. Otherwise, consume only the relevant authoritative portion or contract.

“Mandatory” under Point 03.3 determines **whether** context is required; it never determines representation size. Mandatory context may therefore be satisfied by a bounded authoritative portion when that portion safely carries everything needed for correctness, authority and valid completion.

The following rules are locked:

1. **Active working artifact is always full.** Preserve Point 03.1: the artifact currently being authored, groomed, implemented against, reconciled, verified as the primary object, or reviewed as the primary object is loaded in full.
2. **Architecture still receives the full PRD.** Preserve the deliberate Point 03.1 asymmetry because system-wide requirement interactions may be hidden by aggressive PRD slicing.
3. **Reconciliation candidate assessment requires the full candidate artifact.** /reconcile must judge whether the candidate remains truthful as written under the accepted authority delta; a preselected snippet could hide a contradictory premise elsewhere in the same artifact.
4. **Full dependency/authority artifacts are required only when their relevant semantics cannot be safely bounded.** A clean, self-contained contract such as `CreateOrder(request) -> OrderId` may be consumed as bounded authoritative context. If the contract is ambiguous, qualified elsewhere, distributed across sections, or cannot be interpreted safely without surrounding decisions, expand that source and, if necessary, load it in full as `MANDATORY_ON_DEMAND`.
5. **Whole-artifact-consistency tasks require the full artifact.** Examples include readiness review of that artifact, internal contradiction checks, post-reconciliation coherence assessment, and checking whether all of that artifact's acceptance requirements are satisfied.
6. **A relationship alone never justifies full loading.** `Contains`, `Depends on`, `Governed by` and ancestry identify candidate context sources; the current task determines how much of each source is required.
7. **Escalate representation before scope.** When bounded context proves insufficient, expand that source progressively — relevant section/contract → broader surrounding section → full artifact. Do not respond by indiscriminately loading the parent Epic, full PRD, ADR set or sibling Specs.
8. **“Full artifact” means that artifact only.** Loading a Feature in full does not automatically load its child Specs, parent Epic or referenced ADRs in full. Every additional artifact is independently evaluated under the context rules.

Core rule:

> **Need the artifact itself as the object of reasoning? Load it in full. Need only a particular accepted decision or contract from it? Use bounded authoritative context. If bounded context proves insufficient, progressively expand that source, eventually to the full artifact if required.**

### Locked design — when references are sufficient (Point 03.7)

A reference may remain unresolved when the current operation only needs the identity, location, existence, relationship, or routing information of the referenced source. Once correctness of a semantic decision depends on what the referenced source actually says, Kilo must resolve the reference and read the minimum sufficient authoritative content under Points 03.3–03.6.

The following rules are locked:

1. **References suffice for deterministic mechanics.** Artifact IDs, paths and relationship references are enough for locating artifacts, `Contains`/`Depends on`/`Governed by` traversal, candidate identification, reconciliation closure and routing. No semantic content is required merely to establish these mechanics.
2. **References are not semantic context.** A reference such as `Governed by: ADR-007` identifies where authority lives; it does not communicate what ADR-007 requires.
3. **Mandatory semantic context must eventually be dereferenced.** A reference may represent a `MANDATORY_START` or `MANDATORY_ON_DEMAND` source during assembly/discovery, but before reasoning relies on its contents Kilo must retrieve the bounded authoritative portion required for correctness, or the full artifact where Point 03.6 requires it.
4. **Do not dereference irrelevant references.** Resolve only the references whose contents materially affect the current task. The existence of additional relationships does not justify loading their source content.
5. **A resolved bounded contract is not a bare reference.** `Depends on: SPEC-ORDER-CREATE` is only a locator/relationship. Once the dependency contract matters, the current authoritative contract — for example `CreateOrder(request) -> OrderId` — must be resolved before use.
6. **Delegation prefers references over copied context.** Pass task intent, identifiers, scope and workflow state; the receiving agent resolves its own mandatory context fresh from authoritative state, preserving Points 03.2 and 03.4.
7. **Freshness metadata does not replace content.** A source fingerprint can identify which revision a reference resolves to, but it does not communicate the decision or contract contained by that source.
8. **References are sufficient only when absence of the referenced content cannot change the result.** Practical test: *could reading the referenced source change this valid result?* If no, the reference is sufficient. If yes or uncertain, resolve it as mandatory context before completing that decision path.

Persisted "reference summaries" and context-cache artifacts are explicitly not introduced here; those concerns remain for Point 03.8 and the Point 06 persistence POC.

Relationship between Points 03.6 and 03.7:

> **03.7 decides whether to open the source at all; 03.6 decides how much of it to open once needed.**

Core rule:

> **A reference is sufficient for locating or relating project truth. It is not sufficient when the agent must understand that truth to make the current decision.**

### Locked design — how duplicated context is avoided (Point 03.8)

Deduplicate by provenance, not by semantic similarity. Keep one authoritative source for each decision/contract; reference it elsewhere; resolve each required source only once at its minimum sufficient scope within an invocation; upgrade a bounded representation to full rather than holding both. No persisted convenience copies or generated summaries of authoritative project truth — re-read authoritative sources rather than maintain synchronized semantic duplicates. Disposable indexes/caches (Point 06) may accelerate lookup, but are never authoritative and must be safely rebuildable.

The following rules are locked:

1. **One authoritative home per decision/contract.** Other artifacts point to it via ID/relationship and do not copy its text merely for context convenience.
2. **No persisted context-summary convenience copies.** Do not introduce `context-summary.md`, cached ADR summaries, duplicated PRD excerpts inside Features, or equivalent durable generated summaries of authoritative project truth. This ban is fully general; there are no semantic-summary exceptions.
3. **Dependency metadata identifies, never duplicates.** For example, use `Depends on: SPEC-ORDER-CREATE#CreateOrderContract` rather than copying that dependency contract into metadata. Point 03.7 determines when the referenced contract must be dereferenced.
4. **Deduplicate within one context assembly.** Maintain an invocation-local resolved-source set conceptually keyed by source identity + current fingerprint + resolved scope. If the same source portion is reached through multiple relationships, include its content once while preserving every relationship that led to it.
5. **Broader representation subsumes narrower representation from the same source.** If a bounded portion is already loaded and the full artifact later becomes necessary, upgrade/replace the bounded representation rather than keeping both. Do not add a snippet when the full source is already present.
6. **Do not semantically deduplicate different authoritative artifacts.** Similar-looking PRD, ADR, Epic, Feature or Spec text is not assumed to be equivalent or interchangeable. Provenance determines duplication, not textual or semantic resemblance.
7. **Child artifacts may contain legitimate derived truth.** A Feature's scoped requirements or a Spec's acceptance contract are new authoritative statements at that level when they intentionally refine/decompose upstream truth. They are not treated as duplicate context merely because they trace to a PRD or parent artifact.
8. **Delegation still avoids context forwarding.** Preserve Points 03.2 and 03.4: pass task intent, identifiers, scope and workflow state rather than the caller's expanded context packet. The receiving invocation reconstructs its own minimum-sufficient fresh context.
9. **Cross-invocation caching is disposable acceleration only.** Any cache/index considered under Point 06 must remain non-authoritative, safely rebuildable and incapable of changing the logical context rules. Kilo prefers re-reading authoritative content over maintaining synchronized semantic duplicates.

Core rule:

> **Persist authoritative project truth once, reference it elsewhere, and deduplicate loaded context by provenance within each invocation. Re-reading tokens is preferable to synchronization bugs from durable semantic copies.**

### Locked design — reasonable context ceilings (Point 03.9)

Kilo should normally operate within **20–40k tokens of deliberately assembled project context**. Crossing 40k is allowed when minimum-sufficient correctness requires it and should surface context pressure where the working unit itself appears too broad. **100k tokens is the hard ceiling for one Kilo reasoning unit.** Mandatory context must never be silently discarded to fit the ceiling; if minimum-sufficient context exceeds it, the reasoning scope must be reduced before work continues. Model context-window capacity (200k, 1M, etc.) does not redefine these limits — it is safety headroom, not a budget increase.

| Kilo-managed context | Meaning | Behaviour |
| --- | --- | --- |
| ≤ 40k | Normal | Preferred operating range. |
| >40k–≤100k | Context pressure | Allowed when correctness genuinely requires it. |
| >100k | Ceiling exceeded | Must not proceed as one context packet; scope reduction is required before continuing. |

`SPEC_CONTEXT_PRESSURE` is a diagnostic signal rather than a failure. It fires when either:

1. the Spec artifact materially exceeds the existing **5–15k token guidance**, or
2. grooming, executing or verifying that Spec pushes Kilo-managed working context beyond **40k** because of the Spec's breadth or dependency surface.

Below 100k, work may continue with the pressure surfaced. Above 100k, Kilo must not continue the same reasoning unit by truncating required truth, silently dropping mandatory sources or assuming the model's larger provider window makes the task safe.

Additional boundaries:

- **Count only Kilo-intentionally-assembled context.** The ceiling covers project artifacts, authoritative excerpts, source/code, tests, evidence, dependency contracts, retrieved supporting material and active workflow state. It does not attempt to count system prompts, tool-protocol overhead or model bookkeeping that Kilo does not control.
- **The ceiling is not a fill target.** Kilo deliberately leaves headroom for reasoning, tool interaction and output.
- **Use one common policy.** Do not create separate numeric ceilings for commands or agents. Stage- and role-context rules determine what each workflow needs; some stages may naturally consume more context than others.
- **Do not decide the >100k reduction mechanism here.** Point 03.9 defines the ceiling and required stop condition only. How a large reasoning scope is reduced or assembled is owned by the later context-assembly/grooming design.

Core rule:

> **20–40k is the normal working band; >40k is pressure, not failure; 100k is the hard ceiling for one Kilo-managed reasoning unit. Required truth is never silently discarded to fit the budget.**

### Locked design — large-project context assembly (Point 03.10)

For LARGE projects, context is assembled **task-outward rather than project-inward**. Start with invocation identity and the active working artifact, add the minimum-sufficient portions of its direct authority chain and explicit dependency context, then add the relevant execution surface, and expand only when reasoning establishes a concrete need. Project size alone never justifies loading broader context. Build the source skeleton deterministically from authoritative metadata first, then spend semantic retrieval only on sources whose contents can affect the current result. Existing freshness (03.4/03.5), reference/full-artifact (03.6/03.7), deduplication (03.8), and 40k/100k ceiling (03.9) rules apply throughout.

Assembly layers:

1. **Invocation identity.** Include workflow mode, command/stage, active Project/Epic/Feature/Spec identifiers, current task/intent, and resume/reconciliation state when applicable. Keep this tiny and deterministic.
2. **Active working artifact.** Load it in full under Point 03.6. Existing exceptions and stage rules remain unchanged.
3. **Direct authority chain.** Walk upward only as far as needed. Each ancestor contributes the minimum-sufficient authoritative portion rather than being loaded in full by default. Preserve the Architecture-stage full-PRD exception.
4. **Explicit dependency context.** Resolve declared `Depends on`, `Governed by`, effective inherited governance and relevant pending dependencies mechanically first. Dereference semantic content only when required under Point 03.7. Do not perform repository-wide dependency search.
5. **Execution surface.** For implementation, verification and debugging, discover the source files, interfaces/contracts, tests, configuration and deployment/infrastructure definitions relevant to the active work from the active Spec and repository facts. Do not preload whole directories or subsystems.
6. **On-demand expansion.** Add further context only when reasoning establishes a genuine missing premise. Newly retrieved context joins the same invocation snapshot and follows the existing freshness and deduplication rules.

Context assembly has two phases:

- **Phase A — deterministic skeleton.** Establish the active artifact, parent chain, declared dependencies, governing authorities, workflow state and known implementation/test references from authoritative persisted facts. This phase should not require LLM judgment merely to discover that these sources exist.
- **Phase B — semantic minimum-sufficient resolution.** Decide which referenced sources actually need content, and how much, under Points 03.3–03.7. Semantic retrieval is spent only where source contents can affect the current result.

Explicit anti-patterns:

- no load-all-project-docs-first behaviour
- no full ancestor chain by default
- no all-ADR preload
- no sibling Feature/Spec preload merely because they share a parent
- no repository-wide semantic retrieval before every invocation
- no conversation-history replay as project context
- no generated mega-summary as substitute authority
- no transitive dependency-of-dependency loading unless current reasoning actually reaches that premise

Project size should therefore have little direct relationship to invocation size. A project with many Epics, Features, Specs and years of history should still allow a well-scoped Spec to operate primarily from its own artifact, relevant authority, dependency contracts and execution surface.

Interaction with Point 03.9:

- stop growing the packet once minimum-sufficient context has been reached
- crossing 40k surfaces context pressure but may continue when additional context is genuinely mandatory
- if minimum-sufficient assembly would exceed 100k, return `CONTEXT_CEILING_EXCEEDED` rather than silently truncating required truth

The ceiling report should identify the major contributors and approximate sizes so that later grooming/scope-reduction design has actionable evidence. Point 03.10 does not define how that scope is decomposed or reduced.

Core rule:

> **For LARGE projects, assemble context task-outward: establish the source skeleton deterministically, resolve only the minimum semantic content that can affect the current result, and expand only when a concrete missing premise appears. Project size alone never justifies broader loading.**

### Locked design — agent discovery of additional context (Point 03.11)

Agents discover additional context through a **reason-bound expansion loop**. When current context leaves a concrete premise unresolved, first follow deterministic authoritative references and repository relationships; if the required information is known but its location is not, perform a bounded targeted search. Search results are candidate locators, not context — confirm relevance, resolve the current authoritative source, and load only the minimum-sufficient portion. Further expansion occurs only when newly read material establishes another concrete missing premise. Discovery may expose a `DEPENDENCY_GAP` but must never invent authoritative relationships. Stop when the premise is resolved, further context cannot affect the result, expansion becomes speculative, the context ceiling is reached, or genuine authority ambiguity requires `HUMAN_DECISION_REQUIRED`.

Rules:

1. **State the missing premise first.** Do not begin with open-ended repository exploration. Express the unresolved question specifically enough that additional context has a clear purpose.
2. **Prefer deterministic discovery before search.** Use known artifact/reference IDs, declared dependencies/governance, the direct authority chain, known implementation/test references, imports/callers/interfaces/configuration references, and exact path/name/symbol lookup where applicable.
3. **Use bounded search only when the source location is unknown, not when the information need itself is vague.** Search should answer a concrete question such as where an interface is implemented, where a retry policy is tested, or which accepted requirement defines a particular behavior.
4. **Treat search results as candidate locators, not context.** Confirm candidate relevance, resolve the current authoritative source, load only the minimum-sufficient portion under Points 03.6/03.7, and exclude irrelevant candidates from the active packet.
5. **Chain expansion only when each step earns the next.** A path such as Spec → interface → implementation → configuration is valid when each newly read source demonstrates why the next source matters. Do not recursively explore merely because links exist.
6. **Discovery reveals gaps; it never manufactures project truth.** If code or prose reveals a genuine undeclared semantic dependency, raise `DEPENDENCY_GAP` and repair it through the existing Point 02 process. Do not silently create authoritative `Depends on`/`Governed by` relationships from implementation discovery.
7. **Apply freshness automatically to every newly discovered source.** Resolve its current authoritative source and fingerprint before use; do not rely on remembered or cached content.
8. **Delegated agents discover independently.** The parent passes task intent, scope, identifiers and workflow state rather than an anticipatory expanded packet. The delegated invocation applies the same bounded discovery rules from fresh authoritative state.
9. **Use no arbitrary discovery-count limit.** Do not cap discovery by a fixed number of searches/files. The semantic requirement that every expansion has a concrete reason, plus the 40k/100k context policy, provides the guardrail.
10. **Stop expansion when:** the missing premise is sufficiently resolved; additional material cannot change the current decision; the next step would be speculative; the 100k ceiling would be crossed; deterministic/bounded discovery genuinely cannot locate the required information; or sources conflict/authority becomes unclear. In the last case, use the standing `HUMAN_DECISION_REQUIRED` rule where the ambiguity is workflow-significant.

Core rule:

> **Additional context must be earned by a concrete unresolved premise. Follow deterministic references first, use targeted search only to locate known-needed information, treat results as locators rather than context, and stop expanding as soon as the decision no longer depends on more material.**

### Locked design — token cost interaction (Point 03.12)

Token cost is optimized only **after correctness requirements are satisfied**. Mandatory fresh context is never omitted, replaced by stale summaries, or weakened merely to reduce cost. Kilo minimizes total work-unit cost through minimum-sufficient task-outward assembly, bounded authoritative reads, deterministic lookup, provenance deduplication, reason-bound expansion, appropriate task scope, and economical model selection where capability permits. Optimize total tokens required to reach a correct result, not merely the size of the initial packet. Provider-specific budgets and routing thresholds are deferred to the model-integration/cost design in Point 14.

Rules:

1. **Correctness determines context; cost influences efficiency and model choice only.**
2. **Optimize in this order:** remove irrelevant context; prefer bounded authoritative portions over full artifacts where Point 03.6 permits; deduplicate within-invocation reads; prefer deterministic lookup before semantic discovery; keep work appropriately scoped near the 20–40k normal band; choose a cheaper model when frontier capability is unnecessary; then accept the cost of the minimum-sufficient packet.
3. **Never drop mandatory context for cost.** Do not substitute a stale summary merely because rereading current authority costs more tokens.
4. **Measure cost across the whole invocation/work unit, not just the initial packet.** A smaller starting packet that triggers repeated vague searches may cost more than a larger but well-justified initial packet.
5. **Do not optimize through durable semantic summaries.** Preserve Point 03.8. Disposable Point-06 indexes/caches may reduce lookup cost but cannot replace authoritative semantic content.
6. **Separate invocations rebuild their own bounded packets.** Repeated work under one Feature must not drag the entire previous Feature/session context forward by default.
7. **Model choice may weigh cost but cannot redefine mandatory context.** If a cheaper model cannot reliably handle the minimum-sufficient task/context, use a more capable model or legitimately reduce task scope rather than starving the model of required truth.
8. **Large provider windows do not relax Point 03 discipline.** A larger or more expensive model is not permission to preload unnecessary project context.
9. **Do not define provider-specific monetary or routing thresholds here.** Rupee/dollar caps, token-triggered model switching and provider pricing rules belong to Point 14.
10. **Require lightweight observability for later POC/smoke work.** Capture assembled input tokens, peak context size, expansion count, tokens introduced by expansion, measurable duplicate-context avoidance where practical, and approximate model/API cost where available. Points 06 and 12 determine implementation and validation details.

Core rule:

> **Cost is a tie-breaker among already-correct options. Kilo should minimize total tokens required to reach a correct result, but never by weakening freshness, authority, mandatory context or reasoning validity.**

## [x] 04 — Escalation Model

### Why this matters

AI agents will encounter ambiguities and unexpected implementation problems.

Not every issue should interrupt the developer, but an implementation agent must also not silently make a product or architectural decision simply because it needs to continue coding.

### Locked design — implementation-agent autonomy

An implementation agent may independently resolve a choice only when the choice is clearly an implementation detail within already accepted authority.

All of the following must hold:

- mandatory governing context has been assembled and established as fresh under Point 03;
- the choice is directly consistent with, or genuinely unaddressed by, accepted PRD, architecture/ADRs, Epic, Feature and Spec authority relevant to the task;
- it does not alter required behaviour, acceptance criteria, product semantics or an already accepted decision;
- it does not create, remove or materially change a contract relied upon outside the current implementation scope;
- it does not establish a project-level, cross-cutting or architectural policy;
- changing the decision later would not require migration, compatibility handling, coordinated downstream changes or reinterpretation of accepted authority;
- normal verification can prove the implementation satisfies an already-defined behaviour rather than choosing what that behaviour should mean;
- if classifying the choice as autonomous requires material interpretation, assumptions, debate or a constructed argument, the choice is not autonomous and must be escalated.

Persisted formats, externally consumed API/event/message shapes, deployment/configuration contracts, shared external-facing abstractions and security-related semantics are **presumptively non-local** and therefore cannot be treated as autonomous implementation decisions without an already accepted governing decision.

Tests may independently implement verification of stated behaviour. A test must not resolve ambiguity in governing behaviour by choosing the expected result itself; such ambiguity requires escalation.

Within these boundaries, the agent should choose a reasonable implementation and continue rather than asking the developer to approve routine coding details. The agent does not need to prove its chosen implementation is globally optimal; it needs to establish that the choice is clearly within its implementation authority.

If only part of the implementation encounters a non-autonomous decision, that unresolved portion must remain explicitly blocked. The exact rules for continuing independent safe work, pausing and resuming are defined by the later Point 04 workflow-pause/resume decisions.

Typical autonomous choices include local naming, private helper decomposition, internal code organization, equivalent language/framework idioms, implementation algorithms where required behaviour is already fixed, implementation-local refactoring, test fixtures/mocks, and local performance improvements that preserve accepted behaviour and architecture.

A reusable abstraction may be created autonomously only while it remains implementation-local. Declaring that abstraction to be a shared/project-wide pattern is not an implementation-local decision.

A useful boundary test is:

> **Would any accepted artifact, external consumer, sibling Feature or future implementation legitimately need to know which implementation option was chosen?**

If no, the choice is normally an implementation detail. If yes, it is not autonomous under this rule and must follow the appropriate escalation path defined by the remainder of Point 04.

### Locked design — specification clarification

`SPECIFICATION_CLARIFICATION_REQUIRED` is the initial classification when implementation or verification cannot determine an intended **material observable behaviour** from the accepted Spec and its governing authority.

**Dividing line from 04.1:** Silence is autonomous only when all reasonable choices are implementation-equivalent from the perspective of accepted behaviour and relevant consumers. If reasonable choices produce materially different observable behaviour, the silence requires specification clarification.

Typical triggers:

- required observable behaviour is missing for a case implementation must handle;
- multiple reasonable interpretations would produce materially different results;
- acceptance criteria are insufficient to determine correctness;
- requirements within the Spec contradict each other;
- the Spec conflicts with governing Feature/Epic/PRD authority and the intended contract cannot be determined confidently;
- material state transitions, validation semantics, error behaviour, ordering, retry/idempotency semantics, defaults or boundary behaviour are undefined;
- verification would have to invent the expected result;
- implementation discovers an assumption on which the required behaviour depends but which accepted authority never actually settled.

**De minimis / materiality rule:** A reasonable implementation choice remains autonomous when all of the following hold — no accepted authority constrains the choice; no external consumer, sibling Feature or accepted contract materially relies on which option is chosen; the choice does not establish a shared/project-level convention; changing it later is cheap and local, requiring no migration, compatibility handling or coordinated downstream change; verification of the actual required behaviour does not depend on that specific choice.

**Classification is provisional, not the resolution.** `SPECIFICATION_CLARIFICATION_REQUIRED` means the implementation agent has established the behavioural contract is insufficiently clear to continue that portion safely — it does not mean the agent has determined who resolves it. Triage routes to: Spec clarification (higher authority already determines intent; Spec just needs to state it) / Architecture escalation (choosing requires an architectural decision) / Human-product decision (authority genuinely leaves it open). The implementation agent identifies the ambiguity; it does not choose among the unresolved options.

**Boundary test:** Could two reasonable implementations make materially different promises to a user, consumer, verifier or downstream artifact because this decision was left unstated? If yes → `SPECIFICATION_CLARIFICATION_REQUIRED`. If no, and 04.1 conditions hold → implementation may decide.

### Locked design — architecture issue

An issue is an **architecture issue** when resolving it would establish, change, or materially reinterpret a technical decision that defines a durable system-level constraint, contract, boundary, or pattern beyond the current implementation scope.

The key distinction is:

> **Architecture is not “important technical work.” It is a technical decision whose consequences extend beyond the local implementation and materially constrain how other parts of the system are or will be built.**

Typical architecture issues include:

- introducing or changing a primary persistence strategy or datastore model;
- establishing service/module/process boundaries;
- defining cross-cutting authentication, authorization or security mechanisms;
- introducing a shared integration pattern for external services;
- establishing durable API, event, message or persisted-data contracts;
- deciding consistency, transaction, concurrency or distributed-state strategy;
- changing deployment topology, runtime boundaries or infrastructure architecture;
- establishing project-wide observability, configuration or resilience patterns;
- introducing a framework, platform, shared abstraction or technical pattern that downstream Features are expected to rely upon;
- reversing an earlier architectural choice where migration, compatibility handling or coordinated downstream work would be required.

#### Existing architecture authority is not a new architecture issue

If an accepted ADR or other architecture authority already determines the choice, applying that decision is **not** a new architecture issue.

The implementation agent should follow the existing architecture under 04.1 where the required implementation is clear.

If the existing architecture decision is ambiguous in how it applies to the current Spec, the issue may first classify under `SPECIFICATION_CLARIFICATION_REQUIRED`.

If implementation would need to contradict, extend, reinterpret or replace the accepted architecture decision, then it becomes an architecture escalation.

```text
Architecture topic encountered
        │
        ├─ Existing ADR/architecture clearly answers it
        │      → apply accepted authority
        │
        ├─ Existing authority exists but application is behaviourally unclear
        │      → 04.2 clarification
        │
        └─ Choice requires new/change/reinterpretation of architecture
               → 04.3 architecture issue
```

The overlap is intentional: an ambiguity can initially enter through 04.2 and then triage to architecture when resolving the behavioural uncertainty requires establishing or changing project-wide technical authority.

#### Foundational decisions count even before dependents exist

Architecture does not require multiple existing Features or Specs.

A decision is still architectural when it establishes a foundation that **future reasonable Features/Specs would be expected to inherit or work within**, even if the project currently contains only one implementation scope.

For example, choosing the project's primary datastore, authentication model, deployment topology or service boundary for the first Feature can be architectural because the decision deliberately creates a system-wide constraint for later work.

The counterfactual test is:

> **Would future Features, Specs or implementations reasonably be constrained by this decision if the project grows according to its accepted direction?**

If yes, that is evidence of architectural scope.

#### Non-trigger / materiality rule

Potential reuse alone does **not** make something architectural.

A helper, class, library wrapper, validator, module or abstraction remains implementation-local merely because another Feature *could* reuse it later.

It becomes architectural only when either:

- actual or deliberately intended cross-scope reliance exists; or
- the decision establishes a system-wide technical constraint whose later reversal would require migration, compatibility handling, coordinated downstream changes or reinterpretation of accepted artifacts.

This mirrors the 04.1 boundary:

> **Could this remain a private implementation choice without any accepted artifact, external consumer, sibling/future Feature or project-wide convention needing to know about it?**

If yes, it remains implementation-local.

#### Boundary test

> **Does this decision establish or change a durable technical constraint that current or reasonably foreseeable future implementation scopes must work within, or whose reversal would require coordinated system-level change?**

If yes → architecture issue.

If no → remain under 04.1 unless 04.2 behavioural ambiguity applies.

This gives Point 04 a continuous ladder:

```text
Local technical choice
→ 04.1 implementation autonomy

Required behaviour unclear
→ 04.2 SPECIFICATION_CLARIFICATION_REQUIRED

Required behaviour understood, but resolving it needs a new/change to
a durable system-level technical constraint
→ 04.3 architecture issue
```

### Locked design — what requires human approval (Point 04.4)

Human approval is required when continuing would require Kilo to choose a material project direction that is not already determined by accepted authority and where choosing among reasonable options depends on the developer's priorities, risk tolerance, scope intent, willingness to accept a consequential trade-off, or an explicitly developer-reserved decision.

Architecture and implementation workflows may independently resolve decisions that are genuinely technical and already bounded by accepted project authority.

**Conservative classification rule:** The same conservative-escalation bias from 04.1 applies. If classifying a decision as purely technical requires material argument, interpretation, or an assumption about the developer's unstated priorities, it is not purely technical and must be escalated as `HUMAN_DECISION_REQUIRED`.

**Cumulative-effect rule:** Materiality is assessed against the effective combined consequence of related decisions, not only each in isolation. Several individually minor choices must not be used to incrementally create a materially different cost, lock-in, operational, security, privacy, migration, or risk posture without human approval. The aggregation mechanism is deferred to Points 05/06.

**Developer-reserved decisions:** A decision explicitly reserved for the developer remains human-owned even if an agent later considers one option technically obvious. Durable representation of such reservations is deferred to Point 05's artifact/state metadata design.

**Triggers:** product/scope intent; unsettled material trade-offs; changing accepted authority; material scope creation/removal/deferral; materially different cost/risk/lock-in commitments; authority conflict/ownership ambiguity; explicitly developer-reserved decisions.

**Non-trigger:** Human approval is not required merely because a decision is architectural, important, difficult, or has multiple technically valid solutions.

**Decision-presentation rule:** `HUMAN_DECISION_REQUIRED` must present a bounded decision, not merely report uncertainty. Kilo must state the exact unresolved choice, why existing authority cannot resolve it, the reasonable options, the material consequences/trade-offs of each, and any recommendation or technical preference that can be made without substituting for the developer's judgment. It must ask the developer to choose between concrete alternatives rather than returning a vague "please advise."

Example shape:

```text
HUMAN_DECISION_REQUIRED
Decision: Choose deployment model for X.
Why human-owned: Accepted authority does not establish the preferred
  trade-off between recurring cost and operational burden.
Option A — Managed service: higher recurring cost, lower operational burden, lower maintenance complexity.
Option B — Self-hosted: lower recurring cost, higher operational burden, more maintenance responsibility.
Technical assessment: Both satisfy accepted requirements.
Human decision required: Choose A or B.
```

The resulting authority boundary is:

```text
Can accepted authority + technical reasoning determine it?
→ workflow decides

Does determining it require assumptions about what the developer values,
is willing to pay/operate/risk, or wants the product to become?
→ HUMAN_DECISION_REQUIRED
```

### Locked design — what constitutes a blocking ambiguity (Point 04.5)

Blocking is not a separate escalation category. It is a property of an unresolved 04.2, 04.3, or 04.4 escalation that determines whether dependent work may safely continue while that escalation remains unresolved.

An ambiguity is blocking when continuing the affected work would require Kilo to choose, assume, or encode an unresolved answer that can materially affect the correctness, observable behaviour, contract, architecture, accepted authority, verification result, or developer-owned project direction of that work.

Blocking applies at the narrowest dependency scope whose validity depends on that answer. Independent work that can remain correct regardless of every reasonable resolution consistent with accepted authority may continue. The block widens only where dependency requires it.

An unresolved question is not blocking merely because it is difficult, important, architectural, or currently unknown. If normal bounded discovery can resolve it, or if the current work is invariant under every reasonable resolution consistent with accepted authority, work may continue.

Easy reversibility does not authorize guessing. If continuing requires an assumption the agent is not authorized to make, the dependent path remains blocked even if the speculative implementation would be cheap to undo.

Investigation, option analysis, and genuinely resolution-independent preparation may continue; dependent commitment may not.

If a later accepted resolution reveals that work previously classified as independent was actually affected, the consequences are handled under Point 01 reconciliation.

**Scope semantics** (semantic only — not yet lifecycle states; Point 05 owns state vocabulary):

- **Path block** → only dependent reasoning/implementation stops
- **Work-unit/stage block** → the current Spec/Feature/stage cannot satisfy its gate
- **Project-wide block** → a foundational unresolved decision affects all meaningful next work

**Boundary test:**

```text
Would this work remain correct and truthful under every reasonable
resolution consistent with accepted authority?

YES → not blocked
NO  → blocked
```

### Locked design — how agents report escalation (Point 04.6)

Something cannot be safely self-resolved → classify under 04.2/04.3/04.4 → assess blocking under 04.5 → produce one bounded, actionable escalation report → route to the appropriate owner/workflow.

**Uniform-envelope rule:** Every escalation uses the same report structure regardless of classification. Field presence is fixed; required detail varies by classification — `Options` may be a concise list of interpretations for a specification clarification, while a human decision must include the consequence/trade-off detail required by 04.4.

**Report fields (all always present):**

```text
ESCALATION REPORT

Classification
Origin
Unresolved decision
Why escalation is required
Authority consulted
Options / interpretations
Technical assessment
Blocking assessment
Blocked work
Safe continuation
Resolution required
```

**Depth by type:**

- `SPECIFICATION_CLARIFICATION_REQUIRED` → short interpretations may be enough
- Architecture escalation → materially distinct technical options/constraints
- `HUMAN_DECISION_REQUIRED` → full consequences/trade-offs per 04.4

**Safe-continuation field is mandatory.** The report must explicitly state what independent work may continue. If none exists, it must say `None` and explain why — omission is indistinguishable from failing to assess the 04.5 blocking scope.

**Anti-bundling rule:** Report one smallest actionable decision per escalation, except where 04.4 cumulative materiality is itself the trigger; then report one composite escalation containing all contributing decisions, because the materiality exists only in their combined effect.

**Other governing rules (unchanged):**

- Before escalating, the agent must complete bounded discovery and authority checks already required by Points 03/04 — no escalating merely because the answer wasn't immediately visible.
- Once the escalation threshold is reached, the agent must not keep searching to avoid reporting it.
- Reference authoritative sources; do not copy their content into the report (Point 03 discipline).
- Report conclusions and actionable facts, not a reasoning transcript.
- 04.6 does not define persistence, identifiers, pause mechanics, or resume mechanics — those belong to 04.7–04.9 and Point 05.

**Quality test:** Could the receiving owner understand exactly what must be decided, why it belongs to them, what authority was checked, what is blocked, what may continue, and what resolution is required — without re-investigating the originating task? If yes, sufficient. If no, incomplete.

### Locked design — how the workflow pauses (Point 04.7)

A workflow pause is the execution consequence of a blocking ambiguity under 04.5. It is not a separate escalation type or an automatic project-wide stop.

Kilo pauses the narrowest work scope whose correctness depends on the unresolved decision. Independent work that remains correct under every reasonable resolution consistent with accepted authority may continue.

**Safe-continuation is a standing test, not a snapshot:** Safe-continuation status is not fixed at the time of the original escalation report. Any subsequently identified work may be assessed against the same 04.5 correctness test.

Paused work must not proceed through assumptions, temporary decisions, placeholder contracts, weakened verification, or premature completion. Investigation and genuinely resolution-independent preparation may continue.

A blocked dependency prevents any readiness/completion gate whose validity depends on that dependency from passing. **Gate-deferral exception:** A gate may pass with an unresolved dependency only if the developer has explicitly excluded that dependency from the gate's completion criteria through a 04.4 decision; otherwise it remains blocked.

Pause scope widens only when dependency requires it, never merely because time passes. **If it widens:** update the existing escalation record with the newly dependent work and revised blocking scope rather than creating a duplicate escalation.

If no safe continuation remains in the current invocation, the agent stops cleanly with the outstanding escalation rather than inventing speculative work.

Exact persisted lifecycle/state representation remains deferred to Point 05; 04.7 defines execution semantics only.

**Operational test:**

```text
Does this next action depend on the unresolved answer?

NO  → assess against 04.5; continue if truly invariant
YES → paused
```

### Locked design — how the workflow resumes (Point 04.8)

Workflow resume is a fresh continuation from current authoritative project state after the blocking escalation has been genuinely resolved; it is not a replay of the paused invocation or its old context.

An escalation is considered resolved for resume purposes only when its answer has become durable accepted authority through the mechanism defined by 04.9. Informal, provisional, suggested, or chat-only answers do not release dependent work — including the developer's own chat response, which supplies decision content but not authority until recorded.

Resolution does not automatically restart execution. The developer explicitly resumes the originating workflow through `/continue` or the eventual equivalent command.

Before resuming, Kilo reconstructs minimum-sufficient context from current authoritative state, applies Point 03 freshness rules, re-reads the accepted resolution and relevant changed sources, and reassesses the affected dependency/blocking scope.

Only work whose blocking premise has actually been resolved is released. Other unresolved escalations remain independently blocking.

Previously completed resolution-independent work is preserved when still valid; it is not repeated merely because the workflow resumes. If the accepted resolution reveals that supposedly independent work was actually affected, handle that impact through Point 01 reconciliation rather than silently rewriting it during resume. **If that reconciliation affects work on which the paused path depends, the paused work must remain blocked until reconciliation completes — resuming against unreconciled state is not permitted.**

Control returns to the workflow that originally owned the blocked work. The resolving workflow establishes the accepted decision; it does not take over unrelated downstream execution.

If current authority, repository state, another unresolved escalation, or required reconciliation still prevents safe continuation, the affected path remains paused or produces the appropriate new escalation instead of blindly resuming.

**Operational test:**

```text
Has the resolution been recorded as durable accepted authority?
NO  → remain paused.

YES
 ↓
Has the developer explicitly resumed the owning workflow?
NO  → remain paused.

YES
 ↓
Does current authoritative state show this path is safe to continue?
NO  → remain paused / reconcile / escalate as appropriate.
YES → resume from current state.
```

### Locked design — how resolved escalations become durable project knowledge (Point 04.9)

A resolved escalation becomes durable project knowledge by promoting its accepted resolution into the authoritative artifact that semantically owns the decision. The escalation record itself is historical provenance and routing state; it is not a competing source of project authority.

Decision ownership and decision-maker are separate concerns. A human-owned decision may ultimately belong in a PRD, ADR, Epic, Feature, Spec, or other accepted authority depending on what the decision governs.

An escalation is not resolved for 04.8 resume purposes until the accepted decision has been durably recorded in its authoritative home. Chat responses, provisional conclusions, and the escalation report itself do not satisfy this requirement.

Every legitimately resolved `SPECIFICATION_CLARIFICATION_REQUIRED` requires an update to its owning authoritative artifact, however minimal. If no artifact change is actually necessary, the original issue was not a genuine 04.2 escalation and should have been resolved under 04.1.

If recording the resolution materially changes completed accepted authority, Point 01 reconciliation applies. 04.9 does not bypass completed-artifact immutability. The escalation remains unresolved for dependent resume until the required authority/reconciliation work is complete.

The escalation history retains the original issue, classification, origin/blocking context, a concise historical resolution summary, references to the authoritative resolution, and any reconciliation or scope consequences required to understand why the escalation closed. Exact schema/state fields are deferred to Point 05.

Escalation records persist indefinitely as historical provenance but are not part of default context assembly. They are discoverable on demand under Point 03's minimum-sufficient-context rules; retrieval/indexing mechanics remain deferred to Point 06.

A resolution summary is historical context only. Future workflows resolve current truth from the referenced authoritative artifact, not from the escalation record.

Where one resolution affects multiple authoritative artifacts, normal dependency and reconciliation mechanisms update those artifacts. The escalation record references the resulting authority chain; it does not duplicate that authority.

Rejected options may remain in escalation history as provenance, but they never become accepted project truth.

**Test:**

```text
If the escalation record disappeared tomorrow,
could Kilo still discover the accepted project decision
from normal authoritative artifacts?

YES → durable knowledge is correct.
NO  → the escalation record has accidentally become authority.
```

    — a deterministic, persisted boundary.
  - READY_FOR_FEATURE_DECOMPOSITION → COMPLETE directly is disallowed. An
    Epic with no Features was never actually delivered; that path is
    RETIRE or reconcile, not COMPLETE.
  - COMPLETE does not reopen to ACTIVE. An Epic is a bounded delivery
    episode, not a long-lived container (unlike Project). New meaningful
    work on the same capability becomes a new Epic.
  - COMPLETE → RETIRED remains valid (capability later superseded/obsolete).
  - Any meaningful non-terminal state → RETIRED (human-controlled,
    never inferred from inactivity).
- [x] RETIRED is the only truly terminal EpicState (mirrors Project).
- [x] Post-completion bug fixes / small operational corrections do not
  by themselves require a new Epic — they follow the normal
  maintenance/change workflow. A new Epic is warranted only when the
  new work constitutes a new bounded product/technical outcome.
- [x] Transition metadata/fields deferred to later 05.x items.

### Already agreed — 05.3 Feature states

- [x] FeatureState vocabulary:
  DRAFT, GROOMING, READY_FOR_SPEC, ACTIVE, COMPLETE, RETIRED.
- [x] Meanings:
  - DRAFT — Feature exists; intent/scope preliminary.
  - GROOMING — behaviour, boundaries, acceptance intent, dependencies,
    unknowns, decomposition being clarified.
  - READY_FOR_SPEC — passed the Feature readiness gate (Point 08);
    stable enough to decompose into Specs.
  - ACTIVE — Spec decomposition/delivery has started; live downstream
    work, including the full implement/verify/fix/reverify loop.
  - COMPLETE — integrated Feature outcome delivered; Feature-level
    completion/verification criteria (Point 09) satisfied.
  - RETIRED — intentionally abandoned, superseded, or made obsolete;
    history preserved.
- [x] Explicitly excluded from FeatureState (belong elsewhere): PLANNED,
  PAUSED, BLOCKED, IMPLEMENTING, VERIFYING/VERIFIED, RECONCILING,
  DECISION_REQUIRED, NEW_WORK_REQUIRED, RETIRE_REQUIRED. In particular,
  VERIFYING is not a state — the implement/verify/fix/reverify loop all
  happens within ACTIVE, so the lifecycle isn't turned into an
  execution-status tracker.
- [x] Transitions:
  - DRAFT → GROOMING → READY_FOR_SPEC → ACTIVE → COMPLETE
  - READY_FOR_SPEC → ACTIVE trigger is the first Spec artifact actually
    being created (mirrors Epic's Feature-creation trigger).
  - READY_FOR_SPEC → COMPLETE directly is disallowed — a Feature with no
    Specs was never delivered through the LARGE workflow.
  - COMPLETE does not reopen to ACTIVE. A Feature is a bounded delivery
    outcome; significant later capability becomes a new Feature.
  - COMPLETE → RETIRED remains valid (successful delivery and later
    obsolescence are distinct historical facts).
  - Any meaningful non-terminal state → RETIRED (human-controlled).
- [x] RETIRED is the only truly terminal FeatureState (mirrors Epic/Project).
- [x] Hard completion rule: a Feature cannot become COMPLETE merely
  because every child Spec is COMPLETE — it also requires whatever
  Feature-level integrated verification/acceptance Point 09 defines.
  Exact criteria deferred to Point 09; only the boundary is locked here.
- [x] An ACTIVE Feature may add an additional Spec without moving back to
  GROOMING/READY_FOR_SPEC, provided this does not materially change the
  accepted Feature scope. A material scope change goes through the
  existing reconciliation/escalation rules (Points 01/04) instead.
- [x] Post-completion bug fixes / small operational corrections do not
  by themselves require a new Feature — normal maintenance/change
  workflow applies unless the new work is a new bounded outcome.
- [x] Transition metadata/fields deferred to later 05.x items.

### Already agreed — 05.4 Spec states

- [x] SpecState vocabulary (5 states — deliberately simpler than Epic/Feature):
  DRAFT, READY_FOR_IMPLEMENTATION, ACTIVE, COMPLETE, RETIRED.
- [x] GROOMING intentionally omitted at Spec level. Epic/Feature need
  explicit grooming to resolve ambiguity before decomposition; a Spec
  is itself the output of that decomposition, so DRAFT covers
  "still being clarified."
- [x] Meanings:
  - DRAFT — Spec exists but not yet safe to implement (details,
    acceptance criteria, dependencies, tests, or contract may be
    incomplete).
  - READY_FOR_IMPLEMENTATION — sufficiently complete/unambiguous for
    `/implement` to execute without inventing requirements. Exact
    readiness criteria deferred to Point 08; only the lifecycle
    boundary is locked here.
  - ACTIVE — implementation has started; includes the entire
    implement → verify → fix → reverify cycle.
  - COMPLETE — behaviour implemented and required Spec-level
    verification evidence exists and is applicable (Point 09 defines
    exact evidence).
  - RETIRED — abandoned, superseded, or made obsolete; history retained.
- [x] `/implement` may only start normal implementation on a
  READY_FOR_IMPLEMENTATION Spec — the workflow's core
  requirements-settled-before-coding precondition.
- [x] READY_FOR_IMPLEMENTATION → ACTIVE triggers when `/implement`
  validates the Spec's prerequisites and admits execution — not on
  first source file change, and not on merely invoking `/implement`.
  (Deliberately different trigger shape than Epic/Feature's
  first-child-artifact-created rule, since Spec has no child artifact.)
- [x] Explicitly excluded as SpecState: IMPLEMENTING, VERIFYING,
  VERIFIED, FAILED, FIXING, RECONCILING, BLOCKED, DECISION_REQUIRED.
  A verification failure keeps the Spec ACTIVE; failed evidence /
  outstanding work explains why it isn't COMPLETE yet — no FAILED state.
- [x] Hard completion boundary: a Spec reaches COMPLETE only when its
  agreed behaviour is implemented AND required Spec-level verification
  evidence exists and is applicable — not merely "code is written."
- [x] COMPLETE does not reopen to ACTIVE. COMPLETE → RETIRED remains
  valid. Materially new behaviour later becomes a new Spec under the
  appropriate Feature; small fixes use the normal maintenance workflow.
  No REOPENED state — reconciliation (Section 01's RECONCILE_ONLY)
  handles revision of a completed Spec's accepted claim directly.
- [x] If `/implement` discovers a genuine specification ambiguity on a
  READY_FOR_IMPLEMENTATION Spec, the Spec stays
  READY_FOR_IMPLEMENTATION; the ambiguity is recorded as a
  blocking/escalation record (Section 04), not a demotion to DRAFT.
  Lifecycle state and temporary workflow blockage stay separate.
- [x] Transition metadata/fields deferred to later 05.x items.

### Already agreed — 05.5 Required artifact metadata

- [x] Common required metadata for Project/Epic/Feature/Spec:
  id, type, title, state, created_at, updated_at, parent_id,
  depends_on[], governed_by[].
  - id — stable identifier; exact format deferred to 05.6.
  - type — PROJECT | EPIC | FEATURE | SPEC (not inferred from path/name).
  - title — human-readable name. Renameable; not identity. A rename is
    non-semantic (doesn't imply scope/reconciliation) but is still an
    authoritative-metadata change, so it does bump updated_at.
  - state — one of the states locked in 05.1–05.4.
  - created_at / updated_at — provenance timestamps.
  - parent_id — direct structural parent; null only for Project.
  - depends_on[] / governed_by[] — explicit persisted dependencies
    (Point 02) and accepted governing decisions. Always present,
    empty array (not omitted/optional) when none exist — distinguishes
    "audited, no dependencies" from "field forgotten."
- [x] Project-only additional field: resume_state.
  - null normally; set when Project enters PAUSED to the lifecycle
    state it should return to.
  - Allowed values: DISCOVERY, PLANNING, ACTIVE, MAINTENANCE (the
    states PAUSED can interrupt per 05.1).
  - No generic transition-history mechanism invented to solve this.
- [x] Epic/Feature/Spec require no additional lifecycle metadata beyond
  the common set for v0.2. Their own READY_FOR_* state already marks
  the key boundary. Timestamps like ready_at/completed_at/retired_at/
  started_at are NOT required — Git history covers provenance unless a
  command has an operational need proven later.
- [x] Explicitly excluded from base artifact schema (belong to other
  durable records, are derived, or are project-management scope-creep):
  blocked, block_reason, verification_status, reconciliation_status,
  decision_required, implementation_status, progress_percentage, owner,
  assignee, priority, estimated_effort, planned_start, planned_end.
- [x] updated_at rule: changes only when authoritative semantic content
  or authoritative metadata changes (state, dependency, governance,
  requirement/contract, acceptance criteria, scope, title). Does NOT
  change for spelling/formatting/line-wrap/heading/non-semantic wording
  cleanup. (Feeds the still-open Point 05 material-vs-non-semantic item
  without prematurely resolving it.)
- [x] Contains/children relationships are NOT persisted as metadata —
  only parent_id is persisted; children are derived by reverse lookup
  (matches Point 02's DependsOn/GovernedBy persisted, Contains derived
  rule). Avoids mirrored source-of-truth.
- [x] Physical representation (YAML front matter shape, whether wrapped
  in a `metadata:` key) deferred to the "which state belongs in
  Markdown" item — not locked here, only the field set is.
- [x] Explicitly deferred, not locked: whether artifacts persist forward
  references to reconciliation/evidence records (open_reconciliation_ids,
  verification_evidence_ids) or whether those records reference
  artifacts instead. Current lean is records→artifacts, but this is
  reserved for the reconciliation-related / verification-related state
  items.

### Expected outcome

A state model that lets Kilo reliably answer:

- What is currently being worked on?
- What is ready?
- What is blocked?
- What is complete?
- What requires reconciliation?
- What has already been verified?

without requiring an LLM to reinterpret every document from scratch.

## [ ] 06 — Lightweight SQLite Workflow State & Context Index

### Why this matters

Several v0.2 requirements may require persistent machine-readable state:

- resumable workflows
- artifact lookup
- dependency lookup
- reconciliation
- context assembly
- progress tracking

Repeatedly asking an LLM to read many Markdown files merely to reconstruct this information may waste tokens and introduce nondeterminism.

SQLite may provide a lightweight local solution.

**However, SQLite must earn its place through measurable value.**

### Determine

- [ ] Which state genuinely benefits from SQLite.
- [ ] What must remain authoritative in Markdown/Git.
- [ ] Artifact ID → file path mapping.
- [ ] Minimum relationships required.
- [ ] Workflow checkpoint requirements.
- [ ] Resume-state requirements.
- [ ] Reconciliation-state requirements.
- [ ] Context lookup requirements.
- [ ] Database location.
- [ ] Repository/Git treatment.
- [ ] Recovery behaviour.
- [ ] Rebuild/reindex behaviour.
- [ ] Behaviour when database and Markdown disagree.
- [ ] Whether SQLite materially reduces token/context consumption.

### Required POC

Construct a representative LARGE-project fixture containing:

PRD → Epics → Features → Specs → Architecture decisions → Implementation references → Tests

Then compare Markdown-only context discovery with SQLite-assisted context discovery.

Measure:

- token/context reduction
- retrieval accuracy
- complexity
- maintainability
- failure/recovery behaviour

### Decision gate

SQLite should be adopted only if the POC demonstrates meaningful value.

If Markdown-only state proves sufficiently simple, reliable and inexpensive, SQLite should be rejected.

### Explicit non-goals

v0.2 is **not** building:

- a general-purpose knowledge graph
- a graph database
- a vector database
- a RAG system
- a semantic source-code graph
- a project-management database
- a generic persistence framework

### Expected outcome

Either:

> **Adopt a deliberately small SQLite state/index layer because it demonstrably improves our workflow.**

or:

> **Remain Markdown-only because additional persistence does not justify its complexity.**

Both are valid outcomes.

## [ ] 14 — Claude Integration Strategy & Clean Frontier Handoff

### Why this matters

Claude should be part of the v0.2 workflow alongside GPT because its frontier reasoning and coding capability can add meaningful value to:

- architecture
- difficult debugging
- adversarial review
- high-risk design decisions
- complex implementation review

The economics changed materially with **Claude Opus 5.5**. Anthropic launched Opus 5.5 on September 22, 2026 at lower prices than Opus 5 and also increased subscription usage limits.

The v0.2 goal is therefore **not to decide whether Claude is desirable**. It is.

The goal is to determine the cleanest and most cost-controlled way to make Claude a practical part of this personal workflow.

### Current intended role split

- **GPT** — frontier reasoning, architecture, review, fallback and second opinion.
- **Claude** — frontier reasoning, architecture, difficult debugging, adversarial/independent review and selected complex coding tasks.
- **DeepSeek** — high-volume implementation, tests, routine changes, mechanical work and cost-sensitive iteration.

This is an opinionated personal strategy, not a generic model-routing framework.

### Determine

- [ ] Which workflow stages should deliberately invoke Claude.
- [ ] Which tasks genuinely justify Opus-class capability.
- [ ] When GPT alone is sufficient.
- [ ] When GPT + Claude independent review is worth the extra usage.
- [ ] Whether Claude Code + Claude Pro can provide a clean subscription-backed path.
- [ ] Whether direct Claude API usage is now economically reasonable for selected tasks.
- [ ] Whether a hybrid strategy is preferable.
- [ ] How Kilo prepares a bounded Claude handoff.
- [ ] Minimum required context.
- [ ] Structured handoff format.
- [ ] Structured response format.
- [ ] How Claude results return to the originating Kilo workflow.
- [ ] Non-interactive/headless invocation behaviour.
- [ ] Claude quota/rate-limit handling.
- [ ] API spend limits and cost guardrails.
- [ ] Failure behaviour.
- [ ] GPT fallback behaviour when Claude is temporarily unavailable.
- [ ] Whether manual approval is required anywhere.

### Required POC

Prove a complete controlled handoff:

Kilo → bounded task/context → Claude execution → structured result → Kilo workflow resumes

The POC should establish:

- reliable non-interactive invocation where used
- supported authentication behaviour
- Claude Pro/Claude Code viability
- direct API viability at current Opus 5.5 pricing
- structured output reliability
- context-size behaviour
- error detection
- quota/rate-limit detection
- cost visibility
- clean return of results

### Decision gate

The design decision is **which Claude access path to adopt**, not whether Claude has value.

Preferred order:

1. Use a clean, officially supported Claude Code/Pro path if it integrates reliably with our workflow.
2. If that is unsuitable, evaluate selective direct API use under an explicit budget.
3. If both paths have practical limitations, preserve a clean manual/assisted Claude review path rather than building fragile infrastructure.

Claude should be available to the v0.2 workflow, but **v0.2 must not become structurally dependent on Anthropic availability for basic operation**. If Claude is temporarily unavailable, GPT should allow the workflow to continue.

### Explicit non-goals

Do not turn this into:

- a generic ModelProvider framework
- universal model routing
- a model plugin marketplace
- provider-agnostic orchestration infrastructure
- automatic model benchmarking
- arbitrary agent-to-agent communication

### Expected outcome

A **clean, maintainable and budget-controlled way to use Claude together with GPT and DeepSeek** in the places where Claude materially improves the quality of our personal development workflow.
